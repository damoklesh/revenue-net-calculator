# US-002 — Add internationalization independent of the country

## User Story
As an international user, I want to choose Spanish, French or English so that I can use the application in my preferred language.

## Context
The landing page and routes exist after US-001. UI language and employment/tax country are independent values. Initial supported locales are es, fr and en; amounts use EUR.

Mockup references:
- `docs/mockups/MK-001-app-shell-header-navigation.png`
- `docs/mockups/MK-003-calculator-input-form.png`
- `docs/mockups/MK-009-methodology-page.png`
The language selector is a global UI element and must be visually consistent in the app shell and the main content screens.
Implementation note: Acceptance Criteria take precedence over the mockup if a conflict exists.

Dependency contract: US-001 must already provide the application shell, routes and baseline tests. This story must internationalize those surfaces without coupling locale to salary-country selection. Later stories assume a single reusable translation/formatting layer rather than ad-hoc translated strings.

Use `MK-001`, `MK-003` and `MK-009` only to identify where the global language control appears and how translated content fits in dense forms and documentation pages. The story does not implement the calculator or methodology functionality itself.

## Scope
- In scope: Translation resources, language selection, locale formatting, language preference persistence and document language.
- Out of scope: Changing tax rules based on language, adding countries or persisting salary data automatically.

## Acceptance Criteria
- [ ] AC-1: A visible selector switches es/fr/en on every page; all completed views, errors, help text and results use translation resources.
- [ ] AC-2: On first visit, a supported browser language is selected, including regional variants; unsupported languages fall back to English.
- [ ] AC-3: The explicit language preference is persisted locally. Changing language preserves country, form values and numeric results.
- [ ] AC-4: Intl formats currencies and percentages and document.lang reflects the selected language.
- [ ] AC-5: No untranslated resource keys or stale-language strings are displayed. Unavailable browser storage does not prevent use.

- [ ] AC-6: The language selector occupies the same global shell position across completed routes and exposes its selected state accessibly.
- [ ] AC-7: Translation lookups and number/date formatting are centralized so feature stories can add keys without editing locale-detection logic.

## Technical Notes
- Preserve the existing stack and conventions where present.
- Keep translations under src/locales/{es,fr,en} or the repository's equivalent convention.
- Never use locale selection as a tax-country selector; keep calculation output locale-independent.
- Translate later features when they are implemented; do not implement their functionality in this story.


- Implementation plan:
  1. Identify every user-facing string introduced by US-001 and move it into namespaced translation resources for `en`, `fr` and `es`.
  2. Add a small i18n provider/service with explicit `Locale = 'en' | 'fr' | 'es'`; keep tax country in a separate type/state field.
  3. Resolve initial locale from `navigator.languages`/`navigator.language`, mapping regional variants by base language and falling back to English.
  4. Persist only an explicitly selected locale in a dedicated localStorage key; wrap storage access so exceptions fall back to in-memory state.
  5. Update `document.documentElement.lang` whenever locale changes.
  6. Centralize `Intl.NumberFormat` helpers for EUR, percentages and generic numbers; accept explicit locale rather than reading global browser state inside domain logic.
  7. Place the language selector in the global shell as shown in `MK-001` and ensure later screens inherit it automatically.
  8. Add missing-key behaviour that never exposes raw translation keys in production UI; tests may assert fallback/logging behaviour.
- Prefer resources such as `src/locales/en/*.json`, `src/locales/fr/*.json`, `src/locales/es/*.json` plus `src/i18n/index.ts`/format helpers, or existing equivalents.
- Locale changes must rerender text/formatting only. Do not mutate normalized salary numbers, selected country or calculation state.
