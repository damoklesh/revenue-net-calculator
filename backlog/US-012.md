# US-012 — Save and restore local simulation history

## User Story
As a returning user, I want to save simulations on my device so that I can revisit them later.

## Context
The application has no backend or account system. Saving salary scenarios requires explicit user action; only language preference may already be persisted automatically.

Mockup references:
- `docs/mockups/MK-007-simulation-history.png`
Use the history mockup as the primary reference for saved-simulation listing, restoration actions and privacy messaging.
Implementation note: Acceptance Criteria take precedence over the mockup if a conflict exists.

Dependency contract: US-009 provides serializable normalized inputs, current result metadata and a recalculation entry point. Stored simulations are input snapshots plus provenance, not trusted cached fiscal answers.

Use `MK-007` for list/table structure, selected-item details, restore/delete actions and local-storage privacy messaging. Only implement actions required by this story; mockup-only affordances such as rename/duplicate are optional unless already covered by scope.

## Scope
- In scope: Opt-in local history, up to ten saved simulations, restoration, deletion and storage failure recovery.
- Out of scope: Cloud synchronization, automatic salary persistence and personal tax identifiers.

## Acceptance Criteria
- [ ] AC-1: Explicit Save stores a named simulation and timestamp locally; history supports at most ten simulations and explains when the limit is reached.
- [ ] AC-2: Stored data uses a versioned schema and contains no tax identifiers.
- [ ] AC-3: Restore loads inputs and recalculates. If the rule version changed, it warns rather than presenting an old net value as current.
- [ ] AC-4: Deleting one or all records works; resetting the form does not silently erase saved history.
- [ ] AC-5: Blocked, full or corrupt storage does not prevent calculation and produces a useful recovery message.

- [ ] AC-6: The history view follows `MK-007` for list/detail hierarchy and clearly communicates local-only persistence.
- [ ] AC-7: Storage read/write/delete logic is isolated behind a repository/service abstraction so calculator components do not manipulate raw localStorage JSON.

## Technical Notes
- Preserve the existing stack and conventions where present.
- Use a dedicated versioned localStorage key; validate stored JSON before use.
- Persist normalized inputs and original rule metadata; recalculate through the current engine on restore.
- Never treat saved result values as an authoritative current calculation. Handle storage exceptions explicitly.


- Implementation plan:
  1. Define a versioned persisted schema such as `{schemaVersion, id, name, savedAt, input, rulesetMetadata}`; exclude tax identifiers and avoid treating saved result totals as authoritative.
  2. Implement a `simulationHistoryRepository` abstraction around localStorage with `list/save/delete/deleteAll/get` operations and schema validation on every read.
  3. Cap records at 10 before writing the eleventh; return a structured limit error/message rather than silently evicting unless an existing repository convention explicitly defines eviction.
  4. Save only on explicit user action from a valid current result. Generate stable ids separately from display names.
  5. On restore, load normalized input into the calculator, compare stored/current rule versions, show a warning if changed, and recalculate through the current engine before presenting a current result.
  6. Handle corrupt JSON, obsolete schema, quota errors and blocked storage by isolating/ignoring invalid records and keeping calculation available.
  7. Build history list/detail UI following `MK-007` for required actions: view, restore and delete; implement delete-all with explicit confirmation semantics appropriate to the existing UI conventions.
  8. Keep locale preference storage separate from salary-history storage.
- Add a migration hook/interface even if only schema version 1 exists, so unsupported future versions can fail safely instead of being misread.
