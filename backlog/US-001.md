# US-001 — Create the project scaffold and landing page

## User Story
As a visitor, I want a clear landing page and a reliable application baseline so that I can understand the service and start estimating my net salary.

## Context
The target is NetSalary, a React and TypeScript web application for France and Spain. Inspect the repository before editing: preserve an existing compatible stack; for an empty repository, use Vite, React and TypeScript. The product has no backend, account system or remote salary storage.

Mockup references:
- `docs/mockups/MK-001-app-shell-header-navigation.png`
- `docs/mockups/MK-002-landing-page.png`
Use the shell and landing mockups as the primary visual references for navigation, hero section, reassurance messaging and route entry points.
Implementation note: Acceptance Criteria take precedence over the mockup if a conflict exists.

Dependency contract: this is the bootstrap story. Later stories assume routing, the global application shell, test tooling, static-build scripts and the landing-page entry point created here are stable and reusable. Do not implement salary-domain behaviour as placeholders beyond route-safe stubs.

The implementation should treat `MK-001` as the shell/navigation contract and `MK-002` as the landing-page composition contract. Reproduce hierarchy, spacing intent, navigation placement, trust/privacy messaging and CTA placement; exact pixels are secondary to accessibility and responsive behaviour.

## Scope
- In scope: Project baseline, documented development commands, landing page, navigation and static-host routing.
- Out of scope: Salary formulas, result screens, authentication, backend services and production deployment.

## Acceptance Criteria
- [ ] AC-1: The repository has a runnable React/TypeScript baseline and documented installation, build, lint, type-check and test commands.
- [ ] AC-2: The landing page explains the value proposition, supported countries and three steps of use, with a primary action leading to /calculator.
- [ ] AC-3: Navigation supports /, /calculator and /methodology; unfinished views may use explicitly labelled placeholders until their stories are completed.
- [ ] AC-4: The landing page explains that calculations run on the user's device and does not require registration.
- [ ] AC-5: Unknown routes display a useful 404 view, and documented static-host SPA routing supports direct access and refresh of valid routes.

- [ ] AC-6: The implemented desktop shell and landing-page hierarchy are recognizably consistent with `MK-001` and `MK-002`, while remaining usable at narrow widths without relying on pixel-perfect reproduction.
- [ ] AC-7: Shared shell elements are implemented as reusable components so later routes do not need to duplicate header/navigation markup.

## Technical Notes
- Preserve the existing stack and conventions where present.
- Keep the selected JavaScript/TypeScript stack. A package manifest is appropriate for this target; do not add another language or a server framework.
- Use Vitest and React Testing Library for application tests and Playwright for end-to-end journeys, unless equivalent tooling already exists.
- Configure repository scripts: npm run lint, npm run typecheck, npm test -- --run, npm run build and npm run test:e2e.
- A static-host routing configuration is required; publication is outside this story.


- Implementation plan:
  1. Inspect repository files and package scripts before generating anything; preserve compatible React/TypeScript/Vite conventions if already present.
  2. If the repository is empty, create a Vite React TypeScript baseline with `src/`, `public/`, test configuration and a single package manager lockfile.
  3. Add a router with route components for `/`, `/calculator`, `/methodology` and a catch-all 404. Use lightweight labelled placeholders only for unfinished feature routes.
  4. Build reusable shell components such as `AppShell`, `Header`, `PrimaryNavigation`, `LanguagePlaceholder` and main-content container. Do not implement future locale behaviour here.
  5. Build the landing page from `MK-002`: value proposition, supported countries, three-step explanation, privacy/local-computation reassurance and CTA to `/calculator`.
  6. Add static-host SPA fallback configuration appropriate to the selected deployment target/documentation, without publishing the application.
  7. Document install/dev/lint/typecheck/test/build/e2e commands in README and ensure script names are internally consistent.
- Prefer file boundaries such as `src/app/router.tsx`, `src/components/layout/*`, `src/pages/LandingPage.tsx`, `src/pages/NotFoundPage.tsx` and `src/styles/*`, or the repository's established equivalents.
- Keep shell copy in a form that US-002 can move into translation resources with minimal churn; avoid burying user-facing strings in low-level utility code.
- Implement semantic landmarks (`header`, `nav`, `main`, `footer` where appropriate), visible focus states and keyboard-operable navigation from the start.
- Do not add backend endpoints, authentication SDKs, analytics, salary persistence or tax constants in this story.
