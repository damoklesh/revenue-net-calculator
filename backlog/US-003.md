# US-003 — Capture and validate salary inputs

## User Story
As an employee, I want to enter my gross salary and country so that I can request an estimate for my circumstances.

## Context
The application supports private-sector employees with a constant monetary salary over a complete year and one employer. Automatic tax profiles are initially single, aged 18–64, with no dependants, disability, other income or special deductions. Country-specific assumptions must be displayed and confirmed.

Mockup references:
- `docs/mockups/MK-003-calculator-input-form.png`
Use the calculator-form mockup as the primary reference for form layout, grouping, progressive disclosure and validation-message placement.
Implementation note: Acceptance Criteria take precedence over the mockup if a conflict exists.

Dependency contract: US-002 provides locale selection, translations and formatting helpers. This story owns the normalized salary-input boundary consumed by US-004 and all national calculation stories. Treat the normalized `SalaryInput` model and validation behaviour as a stable domain contract.

Use `MK-003` as the primary functional layout reference. It defines field grouping, country selection, validation-message placement, assumptions messaging and primary/secondary actions. Do not copy values shown in the mockup as fiscal constants.

## Scope
- In scope: Salary form, annual/monthly normalization, country-specific options, validation and stale-result handling.
- Out of scope: Calculation engines, unsupported employment regimes, automatic family-tax calculations and 14-payment schedules before US-010.

## Acceptance Criteria
- [ ] AC-1: Labelled controls capture FR/ES, gross amount, annual/monthly period, age, tax mode and supported country options.
- [ ] AC-2: The canonical annual gross G is within EUR 0–500,000. Zero is accepted and must yield zero bases, contributions, withholding and net when calculated.
- [ ] AC-3: Empty amounts, negative values, non-finite numbers, nonnumeric input and more than two input monetary decimals are rejected with translated errors.
- [ ] AC-4: The form accepts the locale's decimal separator; ambiguous separators are rejected with a valid-format example.
- [ ] AC-5: EUR 3,000 per month with 12 payments normalizes to EUR 36,000 annually without cumulative conversion rounding.
- [ ] AC-6: Changing country preserves annual gross and resets incompatible options. Editing any calculation input invalidates the previous result until recalculation.
- [ ] AC-7: Invalid input and unsupported profiles have distinct messages; automatic mode requires confirmation of its assumptions.

- [ ] AC-8: The rendered calculator form follows the grouping and action hierarchy of `MK-003`, including visible assumptions/help content and inline error placement.
- [ ] AC-9: A single validation/normalization path is used by submit handling and tests; React components do not implement duplicate salary parsing rules.

## Technical Notes
- Preserve the existing stack and conventions where present.
- Normalize to SalaryInput with country, grossAmount, grossPeriod, paymentsPerYear, age, taxMode, manualWithholdingRate and country options.
- France options: cadre/non-cadre and general-regime confirmation. Spain options: monthly contribution group 1–7, ordinary indefinite/fixed-term contract and common-territory confirmation.
- Keep annualGross canonical; initially use 12 payments. Never let an old result appear current after input changes.
- For Spain, exclude daily groups, part-time and special regimes; for France, exclude Alsace-Moselle, overtime, benefits in kind and special contribution agreements.


- Implementation plan:
  1. Define `SalaryInput`, `Country`, `GrossPeriod`, `TaxMode`, France options and Spain options in the domain/application boundary before wiring the form.
  2. Implement locale-aware monetary parsing as a pure function. Accept the selected locale decimal separator; reject mixed/ambiguous separators instead of guessing.
  3. Normalize accepted values into a canonical annual gross and retain enough presentation metadata to redisplay monthly/annual input correctly.
  4. Implement schema/domain validation for gross range, age/profile, manual rate and country-specific option combinations. Return structured error codes translated by the UI.
  5. Build the `/calculator` form following `MK-003`, grouping country, salary, period, age, tax mode and conditional country fields.
  6. When country changes, preserve canonical annual gross, reset incompatible country options to documented defaults and keep locale untouched.
  7. Track a `resultRevision`/dirty flag or equivalent: any calculation-relevant edit marks existing results stale; language-only edits must not.
  8. Require explicit confirmation of automatic-profile assumptions before submit; distinguish validation errors from unsupported-profile messages.
- Prefer a single form-to-domain adapter such as `toSalaryInput(formState, locale)` so submit, tests and later comparison/history flows reuse the same normalization rules.
- Keep 12 payments as the only schedule at this stage. US-010 will extend the input without changing canonical annual gross semantics.
- Do not call national calculation adapters yet; this story may expose a validated submit event/interface consumed later.
