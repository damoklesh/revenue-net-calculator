# US-016 — Validate accessibility and static delivery

## User Story
As a mobile user or a user with accessibility needs, I want the calculator to work without barriers so that I can use it independently.

## Context
Core routes, translations, calculation results and methodology are implemented. The final application must remain a static frontend with no calculation server, secrets or salary telemetry.

Validate the implemented screens against the referenced mockups across mobile, tablet and desktop breakpoints.
Implementation note: Acceptance Criteria take precedence over the mockup if a conflict exists.

Dependency contract: US-001/002/009/014 must be complete before final verification. This is a hardening and delivery-validation story, not a redesign. Fix defects required to meet accessibility/responsiveness/static-hosting criteria while preserving earlier functional contracts.

Use `MK-001`, `MK-002`, `MK-003`, `MK-004` and `MK-009` as desktop intent references; derive tablet/mobile reflow from content priority and accessibility rather than shrinking the desktop composition literally.

## Scope
- In scope: Responsive verification, keyboard and screen-reader behavior, accessibility fixes, static build and README completion.
- Out of scope: Production deployment, backend services, tracking and new fiscal features.

## Acceptance Criteria
- [ ] AC-1: The complete core journey works at 360, 768 and 1280 px without horizontal page overflow.
- [ ] AC-2: Controls have labels, visible keyboard focus, associated errors and result announcements; contrast meets WCAG AA.
- [ ] AC-3: Direct access and refresh of /calculator and /methodology work with the documented SPA hosting configuration.
- [ ] AC-4: The static build contains no secrets or server process and makes no salary, calculation or analytics requests.
- [ ] AC-5: README documents installation, verification commands, supported profiles, versioned rules and hosting route configuration.
- [ ] AC-6: Required checks pass and the principal journeys produce no uncaught console errors.

- [ ] AC-7: Visual regression/manual review confirms the five referenced mockups remain recognizably implemented at desktop after accessibility/responsive fixes.
- [ ] AC-8: A fresh clone can install, verify and build the application using README commands without undocumented local prerequisites beyond the declared runtime/toolchain.

## Technical Notes
- Preserve the existing stack and conventions where present.
- Use Playwright for viewport, routing and network assertions and axe for automated accessibility checks.
- Combine automated checks with manual keyboard, focus, contrast and announcement verification.
- Serve application resources locally; official-reference links are user navigation, not runtime calculation dependencies.
- Preserve the selected frontend stack and existing repository conventions; publishing the build is outside scope.


- Implementation plan:
  1. Run the complete app at 360, 768 and 1280 px and record layout failures before changing code. Fix shared shell/grid primitives before one-off page overrides.
  2. Verify keyboard order, visible focus, skip/navigation behaviour, labels, field-error associations, dialog/drawer semantics if present and result announcements.
  3. Add/execute axe checks on landing, calculator input, populated results and methodology; investigate all serious/critical findings and document any lower-severity residuals.
  4. Verify color contrast for text, controls, status badges, charts and focus indicators. Add non-color labels/patterns where category meaning otherwise depends on color.
  5. Add Playwright journeys for landing -> calculator -> result -> methodology/back plus direct nested-route load/refresh under the documented static-host setup.
  6. Intercept runtime requests during calculation journeys and fail tests on salary/calculation/analytics requests. External official links may navigate only when user activates them.
  7. Inspect production build output/config for secrets, server dependencies and accidental environment payloads; ensure the app can be served as static files.
  8. Bring README up to date with exact toolchain, commands, supported profiles, rule versions/limitations and SPA fallback configuration; validate commands from a clean install.
- Treat the referenced mockups as visual intent at desktop. Accessibility and responsive correctness may require reflow, collapsing navigation or stacking cards without being considered a visual failure.
