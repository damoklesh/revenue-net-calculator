# US-002 — Add internationalization independent of the selected country

## User Story
As an international user, I want to choose Spanish, French or English independently of the selected calculation country so that I can use the application in my preferred language without changing the fiscal rules applied to my salary simulation.

## Context
NetSalary supports France and Spain as calculation countries and Spanish, French and English as interface languages.

Country and language are independent application settings:
- The selected country determines the fiscal, payroll and social-security rules used by the calculation engine.
- The selected language determines only the presentation language, locale formatting and translated user-facing content.

A user calculating a French salary may therefore use the application in Spanish, French or English. Likewise, a user calculating a Spanish salary may use any of the three supported interface languages.

The application must use centralized internationalization resources instead of hard-coded user-facing strings.

Relevant mockups:
- `docs/mockups/MK-001-app-shell-header-navigation.png`
- `docs/mockups/MK-003-calculator-input-form.png`
- `docs/mockups/MK-009-methodology-page.png`

The language selector shown in the mockups with `ES / FR / EN` is part of the intended UI and must remain available globally.

Acceptance Criteria take precedence over mockup content if a conflict exists.

## Scope
- In scope: i18n infrastructure, Spanish/French/English translation resources, global language selector, independent country and language state, locale-aware formatting, browser-language detection, language persistence, document language updates, translated validation and accessibility text, and graceful fallback behavior.
- Out of scope: Additional languages, additional calculation countries, runtime translation editing, external translation services, remote translation loading, automatic translation of user-generated content, and changing fiscal rules when the interface language changes.

## Acceptance Criteria
- [ ] AC-1: The application exposes a visible global language selector with `ES`, `FR` and `EN` on all completed routes, consistent with the referenced mockups.
- [ ] AC-2: Selecting `ES` displays all completed user-facing application content in Spanish without changing the selected calculation country.
- [ ] AC-3: Selecting `FR` displays all completed user-facing application content in French without changing the selected calculation country.
- [ ] AC-4: Selecting `EN` displays all completed user-facing application content in English without changing the selected calculation country.
- [ ] AC-5: Changing language updates the visible application immediately without requiring a page reload.
- [ ] AC-6: Changing language preserves the selected country, form values, current valid result, scenario values and numeric calculation outputs.
- [ ] AC-7: Changing the calculation country does not automatically change the explicitly selected interface language.
- [ ] AC-8: On first visit, the application selects a supported language from the browser locale, including regional variants such as `fr-FR`, `fr-CA`, `es-ES`, `es-MX`, `en-GB` and `en-US`.
- [ ] AC-9: Unsupported browser languages fall back to English when no explicit persisted language preference exists.
- [ ] AC-10: An explicit language selection is persisted locally and restored on the next visit independently of the selected calculation country.
- [ ] AC-11: `document.documentElement.lang` is synchronized with the active interface language and uses `es`, `fr` or `en`.
- [ ] AC-12: Currency, numbers, percentages and dates are formatted according to the active interface locale using `Intl`, while the underlying numeric values remain unchanged.
- [ ] AC-13: Navigation, field labels, helper text, validation messages, buttons, warnings, assumptions, results, empty states, accessibility labels and completed methodology content use translation resources.
- [ ] AC-14: No raw translation keys or stale-language strings are displayed when switching between ES, FR and EN.
- [ ] AC-15: Missing translation resources fall back safely to English without causing an uncaught application error.
- [ ] AC-16: Unavailable or blocked browser storage does not prevent the application from selecting a language or operating normally.
- [ ] AC-17: The calculation engine and country-specific rules are independent from the active interface language; changing only the language produces numerically identical calculation results.
- [ ] AC-18: The language selector is keyboard accessible, has an accessible name, exposes the current selection correctly and preserves visible focus behavior.

## Technical Notes
- Preserve the existing stack and conventions where present.
- Implement this story after US-001 so that the application shell and global navigation already exist.
- Later user stories must reuse this i18n infrastructure instead of introducing local translation mechanisms.
- Use the internationalization library already present in the repository. If none exists, prefer `i18next` with `react-i18next` or an equivalent lightweight React/TypeScript-compatible library.
- Keep translation resources outside React components, for example:
  - `src/locales/es/translation.json`
  - `src/locales/fr/translation.json`
  - `src/locales/en/translation.json`
- English must be configured as the fallback locale.
- Define an explicit supported-language type or constant set, for example:
  - `es`
  - `fr`
  - `en`
- Keep language state independent from country state.
- Do not derive the selected country from the language.
- Do not derive the selected language from the country after the initial application bootstrap.
- The country remains the business-domain value used by the salary calculation engine.
- The language remains a presentation concern.
- Store the explicit language preference under a dedicated local-storage key separate from the selected-country key.
- Suggested startup sequence:
  - Initialize the application shell from US-001.
  - Attempt to read the persisted language preference.
  - If a valid persisted language exists, use it.
  - Otherwise inspect `navigator.languages` and `navigator.language`.
  - Normalize regional variants to the supported base language.
  - Map any `es-*` locale to `es`.
  - Map any `fr-*` locale to `fr`.
  - Map any `en-*` locale to `en`.
  - Fall back to `en` for unsupported browser languages.
  - Initialize the i18n provider with the resolved language.
  - Synchronize `document.documentElement.lang`.
- When the user changes language:
  - Update the i18n active language.
  - Persist the language preference when browser storage is available.
  - Update `document.documentElement.lang`.
  - Re-render all user-facing strings.
  - Reformat displayed currencies, numbers, percentages and dates.
  - Preserve country state.
  - Preserve canonical form values.
  - Preserve valid calculation results.
  - Do not trigger recalculation solely because the language changed.
- When the user changes country:
  - Apply the country-specific behavior defined by the relevant salary-input story.
  - Keep the currently selected interface language unchanged.
  - Reset only country-specific incompatible fields where required by the corresponding country/input logic.
- Use a centralized locale mapping for formatting:
  - `es -> es-ES`
  - `fr -> fr-FR`
  - `en -> en-GB` or the repository's documented English formatting locale.
- Use `Intl.NumberFormat` for:
  - EUR currency
  - percentages
  - general numeric output
- Use `Intl.DateTimeFormat` for dates.
- Never parse formatted output strings back into calculation-domain values.
- Keep calculation inputs and results in canonical numeric form independent of locale.
- Input parsing rules for decimal separators belong to the salary-input validation story, but this story must expose the active locale so those rules can consume it later.
- Translation keys must be semantic and stable rather than based directly on English text.
- Recommended key namespaces include:
  - `navigation.home`
  - `navigation.calculator`
  - `navigation.methodology`
  - `navigation.history`
  - `language.spanish`
  - `language.french`
  - `language.english`
  - `calculator.*`
  - `results.*`
  - `methodology.*`
  - `validation.*`
  - `common.actions.*`
- Do not build sentences by concatenating independently translated fragments when grammar may differ between languages.
- Use interpolation for dynamic values.
- Accessibility strings such as `aria-label`, screen-reader-only text, status announcements and validation descriptions are user-facing content and must use translation resources.
- Do not translate:
  - internal IDs
  - ISO country codes stored in domain objects
  - tax-rule identifiers
  - calculation rule versions
  - machine-readable property names unless another user story explicitly requires localized export headers
- `MK-001` defines the global placement and visual treatment of the ES/FR/EN language selector.
- `MK-003` defines form hierarchy and demonstrates where translated labels, helper text and validation feedback appear.
- `MK-009` defines the methodology page structure and demonstrates translated headings, explanatory content and navigation while official institution names and source URLs remain authoritative.
- If the current implementation contains hard-coded strings introduced by US-001, migrate those strings into the translation resources in this story.
- Add reusable test helpers capable of rendering the application with:
  - a selected language
  - a selected country
  - optional persisted preferences
- Keep translation resources bundled locally with the static application.
- Do not fetch translations from a server or CDN at runtime.
- The expected state matrix must support all six country/language combinations:
  - France + Spanish
  - France + French
  - France + English
  - Spain + Spanish
  - Spain + French
  - Spain + English
- Treat all six combinations as valid application states.
- The implementation must not contain conditional logic such as `if country === FR then language = fr`.
- The only automatic language resolution occurs during first-load initialization when no explicit persisted language preference exists.
