# US-004 — Create the calculation engine and versioned rules

## User Story
As a maintainer, I want calculation rules separated from the interface so that I can update parameters and add country adapters without rewriting views.

## Context
The selected target is a static React/TypeScript application. Tax calculations must execute locally. The starting reference snapshot was checked on 2026-09-30; this story introduces the engine contract, not complete national formulas.

Mockup references:
- No dedicated mockup required for this story.
No dedicated mockup is required for this story because it is an engine and ruleset architecture story.
Implementation note: Acceptance Criteria take precedence over the mockup if a conflict exists.

Dependency contract: US-001 provides the TypeScript project and test runner. US-003 may be developed separately, so engine contracts should be defined in domain terms and exported cleanly; avoid importing React form components. US-005 through US-010 depend on the contracts, rounding rules and ruleset metadata introduced here.

There is intentionally no dedicated visual mockup. Correctness, determinism and adapter isolation are the acceptance surface.

## Scope
- In scope: Pure engine contracts, rule schemas, local version metadata, decimal/rounding policy and domain errors.
- Out of scope: Implementing all national formulas, remote rule fetching, arbitrary executable expressions and new country UI.

## Acceptance Criteria
- [ ] AC-1: A common calculateSalary(input, ruleset) contract delegates to pure national adapters without React or network dependencies.
- [ ] AC-2: Local rule sets include id, country, version, effectiveFrom, effectiveTo, incomeYear, publicationYear, verifiedAt, sources and assumptions; open-ended dates may be null.
- [ ] AC-3: Schemas reject invalid rates, unordered or overlapping brackets, non-finite numbers and missing required parameters; unavailable rules produce a typed domain error.
- [ ] AC-4: Identical normalized input and rule version produce identical numeric output, deduction lines, bases, assumptions and warnings.
- [ ] AC-5: A documented rounding policy reconciles monetary totals in cents and assigns payment-schedule rounding residues to the final payment.
- [ ] AC-6: A hypothetical adapter in a test can be registered without modifying presentation components or FR/ES adapters.

- [ ] AC-7: Adapter registration, ruleset lookup and schema validation are independently unit-testable and do not require rendering the application.
- [ ] AC-8: Domain errors have stable machine-readable codes plus human-safe metadata so UI stories can translate messages without matching raw exception text.

## Technical Notes
- Preserve the existing stack and conventions where present.
- Keep pure calculations under src/domain and local parameter sets under src/rules, or existing equivalents.
- SalaryResult includes annualGross, annualContributions, nullable annualWithholding and annualEstimatedIncomeTax, annualNetBeforeTax, annualNetAfterTax, monthlyAverageNet, paymentSchedule, deductionLines, rulesetId, assumptions and warnings.
- Only one of withholding or projected annual tax is applied at a time. Tax-base deductions are not cash deductions.
- Zero gross short-circuits national minimum contribution bases. Use decimal arithmetic or integer cents where appropriate; do not rely on binary floating-point rounding.
- French contribution parameters are 2026; annual IR projection uses the enacted 2026 assessment scale for 2025 income, labelled as a projection. Spanish withholding uses the algorithm effective 2026-09-10.


- Implementation plan:
  1. Create presentation-neutral domain types for normalized inputs, results, deduction lines, assumptions, warnings and typed errors.
  2. Define a `RulesetMetadata` contract with all required fields and country-specific validated payloads.
  3. Implement schema validation at ruleset load/registration time, including finite numeric checks, non-negative rates, ordered brackets and no overlaps.
  4. Define an adapter interface such as `CountrySalaryAdapter.calculate(input, ruleset)` and an adapter registry keyed by country.
  5. Implement `calculateSalary(input, ruleset)` as an orchestration function that validates country/ruleset compatibility and delegates to the registered adapter.
  6. Introduce deterministic money helpers using integer cents or a decimal library already accepted by the repository. Document where intermediate precision is retained and where half-up cent rounding occurs.
  7. Add reconciliation helpers for annual totals and payment schedules; allocate unavoidable cent residue to the final payment only.
  8. Add a minimal test adapter/fixture solely to prove registration/extensibility; do not implement France or Spain formulas here.
- Prefer `src/domain/*`, `src/rules/*`, `src/calculation/*` (or existing equivalents) with no imports from React, router, localStorage or network modules.
- Domain error examples should include `RULESET_INVALID`, `RULESET_UNAVAILABLE`, `COUNTRY_ADAPTER_MISSING`, `UNSUPPORTED_PROFILE` and `CALCULATION_INVARIANT_FAILED`, or equivalent stable codes.
- Every calculation result should carry `rulesetId`, assumptions and warnings from the actual executed path.
